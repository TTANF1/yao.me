最近看了 DeepSeek Harness 团队发的那篇 Super-agent 的技术文章，以及昨天又刷到一个团队说，他们最近从产品端与AI聊需求，然后将同一个 session 流转到设计侧，再流转到开发手上，在模型拥有了全链路的 context 时，每个环节可能沟通上会导致的信息衰减和歧义，影响可能会变小到忽略不计了。

在结合我之前的经历，联调时，后端直接丢来一个AI吐出来的文档，语义也不明确，还杂糅了一些后端设计的内部逻辑，完全是一片充满噪音的，名义上的“接口文档”。你去问文档中具体的问题，他清楚个der，都是agent跑出来的结果。再到后来，就直接让你去跟他的 agent 对话，问你想要的数据或信息。。。

第一，我并不排斥在技术飞速发展的当下，不管是协助方式，开发流程，都会发生巨大的改变。改变意味着风险，摩擦，当然也是进步的必经之路。但是完全对自己的产物，要用来与他人联调沟通的内容不负责，不了解，是我所不能接受的。

所以，在看到需求上下链路，共用 session 的这个方案时，一下就击中了我。

但是随之而来的想法便是，这种全链路共用 session 的方案，上下文内容一定会很长。如何在减少重要信息损耗的同时，在什么节点来压缩上下文？中途想要注入擅长其他能力的其他模型 tools 或者执行结果时，这块内容要怎么设计？以及，怎么治理不同角色在同个session中的权限？因为总不能，设计同学聊着聊着把需求直接变更了；产品同学回头突然想调整一下需求，聊完直接把代码也改完了。。。

如果你要说，这以后不都是一个人的活么，都一样[doge]。那当我没说。

扯回来到 Super-agent。

我目前认为的所谓 agent 哈，还是在传统系统设计，技术架构中替换了一个关键节点，一颗“无限煌心”——LLM。

其实在其他的“人偶部分”，还是函数方法封装复用（Tool calling），pipe 工作流节点设计（ReAct），权限管理，数据清洗，事件监听布拉布拉布拉。
当然我不是说这两者孰轻孰重，像 Super-agent 就是根据业务场景，来组合搭配不同的架构设计理念，以达到某些场景的指标提升和设计优化。想出这样的设计并落地，也不是一件简单的事情。把庞大而复杂的系统设计，浓缩成一篇通俗易懂的技术文章，让技术人能共同学习进步，我也要振臂高呼：牛逼！

这种产教结合的经验，就是我可能日后在某个类似场景下的醍醐灌顶。

现在，实现产品或某种工具的成本被降到了最低，而能发现需求——将不易被人察觉的，抽象的想法，思考并转变为落实的一条条具体的“规则”。agent 就是这一条条“规则”的具象化体现。
在开发我日常真正会使用到的 agent 时，那种你知道它最终要达成什么效果时。在中途遇到的各种技术上的问题，感觉都不是问题，在 codex 和 claude 的帮助下，一路超高效率的过关斩将，快速根据当前情况、异常做出决断，有问题可以马上总结并重试或者切换尝试路径。真的有一种运筹帷幄，睥睨全局的感觉。
我擅长这种遇到问题解决问题的成长路径，我也喜欢这种。

大多数文章到了结尾应该要进入总结，升华阶段了。
总结 emm。
在前进中感受阻碍，在阻碍中总结，总结后成长，直到经济上躺平。
